# 입찰 낙찰/패찰 판정 + 개인 바이어스 보정 — 설계

## 배경

`bid_participations`(Supabase)에 참가상태(참가예정/참가완료/패스)와 제출입찰가를 기록하는 기능은 이미 있다. 하지만 참가완료한 건이 실제로 낙찰됐는지 패찰했는지는 아무 데도 표시되지 않고, 우리가 제출한 가격과 실제 낙찰가의 격차를 다음 추천가 산정에 활용하지도 못하고 있다.

`app/api/bids`가 이미 Notion에서 읽어오는 `낙찰업체`/`실제낙찰금액`/`실제낙찰률` 필드(bid-monitor가 매일 자동으로 채워 넣음)를 활용하면, 나라장터 로그인·스크래핑 없이도 이 문제를 풀 수 있다는 것을 조사로 확인했다.

**조사 결과 (참고, 별도 구현 없음)**: 나라장터 공개 API(`getOpengResultListInfoServc`)는 공고당 낙찰(성공)업체 1곳의 정보만 제공하며, 경쟁입찰에서 패찰한 업체의 개별 투찰금액은 공개 API로 조회 불가능하다(나라장터 로그인 후 본인 계정에서만 확인 가능 — 로그인 자동화는 계정 자격증명 보안 리스크와 UI 변경 시 매번 깨지는 유지보수 부담 때문에 이번 범위에서 제외). 따라서 "우리가 제출한 가격"은 계속 사용자가 직접 입력하는 방식(기존 `참가완료` 플로우)을 유지하고, 이 설계는 그 위에 낙찰/패찰 판정과 개인화 보정만 얹는다.

## 목표

1. 참가완료한 건에 대해 낙찰/패찰/결과대기를 자동으로 판정해 표시한다.
2. 패찰한 건들의 "우리 제출률 vs 실제낙찰률" 격차를 평균 내어, 다음 추천가에 개인화 보정을 얹은 "개인화 추천가"를 함께 보여준다.

## 회사 식별 정보

- 상호명: `LV LAB건축사사무소`
- 사업자등록번호: `694-46-01379` (이번 판정은 상호명 문자열 비교만 쓰고, 사업자등록번호는 참고로 코드 주석에만 남긴다 — Notion `낙찰업체` 필드가 상호명 텍스트만 담고 있어 사업자등록번호 비교 대상이 없음)

## 낙찰/패찰 판정 로직

새 Supabase 컬럼이나 저장 로직 없이, **매 렌더링 시 파생 계산**한다 (이미 로드된 `bids`(Notion)와 `participations`(Supabase)를 조인해서 즉석 계산):

```ts
type Outcome = '낙찰' | '패찰' | '결과대기';

function deriveOutcome(bid: BidItem, p: BidParticipation | undefined): Outcome | null {
  if (p?.status !== '참가완료') return null; // 참가완료 건만 판정 대상
  if (!bid.낙찰업체) return '결과대기';       // 아직 개찰 결과 없음
  return bid.낙찰업체.trim() === 'LV LAB건축사사무소' ? '낙찰' : '패찰';
}
```

- `낙찰업체` 문자열은 trim만 하고 정확히 일치할 때만 "낙찰"로 판정한다 (부분일치·유사매칭은 하지 않음 — 오탐 방지가 우선).
- `참가예정`/`패스` 상태에는 이 판정을 적용하지 않는다 (참가완료 건에만 의미가 있음).

## 개인 바이어스 보정

패찰로 판정된 건 중 `실제낙찰금액`과 `실제낙찰률`이 모두 존재하는 건만 대상으로 한다.

```ts
// 우리가 써낸 비율을 실제낙찰률·실제낙찰금액 비율로 역산 (예정가격 필드 없이 계산 가능)
우리제출률 = 실제낙찰률 * (제출입찰가 / 실제낙찰금액)
격차(%p) = 우리제출률 - 실제낙찰률
```

- 이런 격차값을 가진 패찰 건이 **3건 이상**일 때만 바이어스를 계산해서 적용한다 (`bias = 격차값들의 평균`). 3건 미만이면 개인화 추천가를 아예 표시하지 않는다 (표본 부족한 상태에서 잘못된 보정을 보여주는 것보다 안 보여주는 게 안전).
- 개인화 추천가는 기존 `추천입찰가`에 비율로 근사 적용한다: `개인화추천가 = round(추천입찰가 * (1 + bias / 100))`. 정확한 예정가격 기준 재계산이 아니라 근사치이며, 그 사실을 UI 문구("근사치")로 명시한다.
- 이 계산은 전역적으로 한 번(모든 패찰 건 대상) 수행하며, 공고별로 다시 계산하지 않는다 — "우리의 평균 입찰 성향"이라는 하나의 숫자를 모든 카드에 동일하게 적용한다.

## UI 변경

### 카드에 결과 배지 추가

기존 참가상태 배지(`BidParticipationControl`) 옆에, `상태==='참가완료'`이고 `deriveOutcome`이 non-null일 때만 결과 배지를 추가로 표시:
- 낙찰 → 초록 계열
- 패찰 → 회색/빨강 계열 (기존 `실제낙찰금액` 표시색인 초록과 구분되는 색)
- 결과대기 → 옅은 회색

### 개인화 추천가 표시

`BidsView`에서 전역적으로 bias를 한 번 계산해 두고(패찰 표본 3건 이상일 때만 값이 나옴), 카드의 기존 `추천입찰가` 표시 옆에 병기:

```
추천입찰가 1,234만 (88.13%)  개인화 1,198만 (근사, 패찰 4건 평균 -2.9%p 반영)
```

표본이 3건 미만이면 이 줄 자체를 렌더링하지 않는다.

## 범위 밖

- 나라장터 로그인 기반 스크래핑(개별 패찰 업체 투찰금액 전수 조사)은 하지 않는다.
- bid-monitor(`analyze-price.js`)의 추천가 계산 로직 자체는 수정하지 않는다 — 개인화 보정은 arch-reference 화면 표시 레이어에서만 얹는다.
- Supabase 스키마 변경 없음(신규 컬럼 없음) — 전부 파생 계산.
- 낙찰/패찰 상태를 Notion에 다시 쓰지 않는다 (읽기 전용 유지).

## 테스트 / 검증 방침

자동화 테스트 없음. 검증은:
1. `npx tsc --noEmit` / `npm run build`
2. 브라우저에서: 참가완료로 표시해둔 실제 과거 건(예: 이미 개찰 완료된 건) 중 낙찰업체가 채워진 것으로 낙찰/패찰 배지가 올바르게 뜨는지 확인
3. 패찰 표본이 3건 미만일 때 개인화 추천가 줄이 안 뜨는지, 3건 이상 채워지면 뜨는지 (테스트를 위해 임시로 여러 건을 참가완료+제출가로 마킹해서 확인 후 정리)
